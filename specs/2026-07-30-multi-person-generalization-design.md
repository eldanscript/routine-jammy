# routine-jammy v2 — 다중 사용자 일반화 설계

Date: 2026-07-30
Status: 설계 확정 (구현 계획 수립 대기)

## 목표

특정인(배우자) 전용 앱을 **지인 규모(수명~수십명)의 다중 사용자 앱**으로 일반화한다.
사람마다 관리하는 루틴이 다르고 선호가 다르므로, 루틴 구성·조정 규칙·테마가 모두 개인별로
달라야 한다.

**비목표 (명시적 제외)**: 공개 셀프서비스 전환(회원가입·로그인·유저별 DB). 신뢰 모델은 현재와
동일하게 "고유 링크를 아는 사람 = 그 사람"이며, Apps Script + Google Sheets 스택을 유지한다.
BaaS/백엔드 이전은 이 사이클 범위 밖이다.

## 확정된 제약

### C-1. 기존 사용자의 UI 기능 동일성 (하드 제약)

기존 사용자(배우자, `personId: jammy`)는 **화면에서 보이는 기능과 값이 마이그레이션 전후로
동일**해야 한다.
구체적으로 완료율, 운동 연속일수, 리포트 탭 내용, 주간 이력이 같은 값을 보여야 한다.

- URL 변경은 허용된다 (홈화면 재추가 필요 시 오퍼레이터가 직접 처리 가능한 관계).
- 데이터 스키마 변경은 허용된다 — 단 **기존 데이터 마이그레이션이 반드시 동반**되어야 한다.
- 백엔드 내부 구조 변경(규칙 엔진 카탈로그화, 크론 루프화, 시트 스키마 확장)은 화면에
  드러나지 않는 한 자유롭다.

충돌 시 우선순위: **기존 사용자 UI 동일성 > 새 기능**.

### C-2. 주간 자동화는 무인 실행을 유지한다

현재 `OS crontab → weekly_refresh.py`가 Claude 세션 없이 순수 Python으로 돌고 있다. 이
성질을 유지한다 — 사람이 늘어도 매주 LLM 세션이 사람 수만큼 필요해지는 구조로 바꾸지
않는다. (온보딩은 예외: 신규 사용자 추가 시에만 rainny/agent가 대화로 설계한다.)

### C-3. Apps Script 배포와 스프레드시트는 1개를 유지한다

Apps Script 웹앱 배포는 자동화가 불가능하고 사용자가 script.google.com에서 수동으로 해야
한다. 사람마다 배포/시트를 분리하면 신규 사용자 추가마다 이 수동 단계가 반복되어 확장이
막힌다. 따라서 배포·시트는 단일하게 두고 `person` 차원으로 네임스페이스만 나눈다.

## 설계

### S-1. 아이템 카탈로그 + 규칙 템플릿

현재 `src/routine-jammy/routine_rules.py`는 배우자 전용으로 하드코딩되어 있다:

```python
CATEGORIES = ["슬로우 조깅", "스쿼트", "데드리프트", "런지", "플랭크", "간식섭취", "바이올린"]
_SUGGESTIONS = {"바이올린": "...", "간식섭취": "..."}
```

이를 **아이템 카탈로그**로 분리한다. 카탈로그는 "선택 가능한 루틴 아이템 종류"의 마스터
목록이며, 각 아이템은 다음을 가진다:

| 필드 | 의미 |
|---|---|
| `id` | 안정적 식별자 (이력 조인 키 — 변경 시 그 아이템의 이력이 끊긴다) |
| `label` | 화면 표시명 |
| `group` | 분류: `exercise` / `meal` / `other` |
| `ruleType` | 아래 규칙 템플릿 중 하나 |
| `suggestion` | 조정 제안 문구 (한국어, 사람이 미리 작성). **선택 필드** — 없으면 그 아이템은 완료율 집계에는 들어가지만 조정 제안은 생성하지 않는다(현재 조깅·스쿼트 등 5개 항목이 이 상태) |

**규칙 템플릿** (조정 로직의 종류):

| ruleType | 완료율 집계 | 조정 트리거 | 조정 방향 |
|---|---|---|---|
| `binaryCheck` | 포함 (체크된 일수 / 7) | 2주 연속 완료율 50% 미만 | 완화 제안 (현재 로직과 동일) |
| `timedPractice` | 포함 (체크된 일수 / 7) | 2주 연속 완료율 50% 미만 | 시간/분량 축소 제안 |
| `logging` | **제외** | **주당** 기록 일수 3일 미만이 2주 연속 | 리마인드 제안 |

`binaryCheck`와 `timedPractice`는 판정 기준이 동일하고 제안 문구의 성격만 다르다 — 임계값
(50%)·관측 창(2주)은 현재 `find_low_categories(threshold=0.5)`와 같게 유지한다.

`logging`은 체크박스가 아니라 자유 텍스트 입력(현재 식단 노트 `아점`/`저녁` textarea)이라
"체크 여부"가 존재하지 않는다. 따라서 완료율 집계에서 제외하고, **입력이 비어있지 않은
일수**를 별도로 세어 판정한다. 3일 미만을 임계값으로 두는 이유: 완료율과 달리 기록은 매일
채우기 어려운 성격이라 50%(3.5일)보다 관대해야 하고, 정수 일수로 판정해야 모호함이 없다.

**판정 단위는 "주 단위 독립 판정"이다 — 2주 합산이 아니다.** 기존 `find_low_categories`가
"이번 주 < 50% **그리고** 지난 주 < 50%"로 각 주를 독립적으로 보는 것과 동일한 구조를
따른다. 즉 `logging`의 트리거는 **"주당 기록 3일 미만"이 2주 연속될 때**다. 한 주라도 3일
이상 기록하면 그 주는 통과이며 연속이 끊긴다. (2주 통틀어 3일이라는 뜻이 아니다.)

> **`logging`의 판정 범위는 "조정 제안을 낼지"에만 한정된다.** 식단 노트의 본체 기능인
> **영양분석 파이프라인은 그대로 유지되며 사람별로 동작한다** — `extract_meal_log`(아점/저녁
> 텍스트 추출) → `parse_meal_segments`(음식명·수량 파싱) → `estimate_meal_nutrition`
> (식품영양성분DB 조회, 100g 기준 스케일링) → 주간 평균 kcal/탄단지 + 매칭 실패 항목 +
> 권고(`weekly_macro_recommendations`) → `docs/data/<personId>/nutrition-stats.json` →
> 리포트 탭. 이 경로는 `ruleType`과 무관하게 `group: meal` 아이템이 있는 모든 사람에게
> 동작한다. "기록 일수 3일 미만" 판정은 오직 *"이 사람에게 식단 기록 리마인드를 제안할지"*를
> 결정할 뿐, 영양분석을 켜고 끄지 않는다.

현재 식단 노트는 완료율 집계에 들어가 있지 않으므로(`CATEGORIES`에 없다), `logging`을
도입해도 **배우자의 완료율 숫자는 변하지 않는다**(C-1 충족). 다만 조정 제안은 새로 생길 수
있다 — 이는 화면 기능 변화가 아니라 제안 내용의 추가이며, 배우자 마이그레이션에서는 식단
노트에 `suggestion`을 비워 등록해 **현재와 동일하게 제안이 생기지 않도록** 한다.

한 사람의 루틴 = **카탈로그에서 고른 아이템 목록 + 아이템별 개인 목표값**(예: 조깅 25분 vs
30분). 카탈로그에 없는 아이템이 필요하면 온보딩 시 rainny/agent가 카탈로그에 추가한다.

**배우자 마이그레이션**: 현재 7개 카테고리를 카탈로그 아이템으로 1:1 변환한다 —
슬로우 조깅·스쿼트·데드리프트·런지·플랭크는 `binaryCheck`(제안 문구 없음, 현재도 없음),
간식섭취는 `binaryCheck` + 기존 제안 문구, 바이올린은 `timedPractice` + 기존 제안 문구,
식단 노트(아점·저녁)는 `logging` + 제안 문구 없음. **카탈로그 아이템 `id`는 현재
`CATEGORIES`의 문자열을 그대로 쓴다**(예: `id: "슬로우 조깅"`) — 시트의 기존 체크인 행이
이 문자열을 `item` 값으로 담고 있어서, id를 새로 만들면 과거 이력과 조인되지 않는다.
이렇게 하면 **완료율과 조정 제안 결과가 현재와 완전히 동일**하다(C-1 충족).

### S-2. 사람별 설정과 데이터 격리

**사람 설정 파일** `people/<personId>.json`:

| 필드 | 의미 |
|---|---|
| `personId` | URL·시트·이력의 조인 키. 변경 금지(변경 시 이력 단절) |
| `displayName` | 화면 표시 이름 |
| `items` | 선택한 카탈로그 아이템 id 목록 + 아이템별 목표값 |
| `themeId` | S-3의 테마 식별자 (`wellness`/`travel`/`space`/`urban`/`cinema`/`study`, jammy는 `pastel`) |
| `active` | false면 주간 크론이 건너뛴다 (탈퇴/일시중지) |

`people/`는 실제 사람의 루틴 구성이 담기므로 커밋 대상이다. 단 CLAUDE.md의 기존 금지사항
("대상 사용자의 실제 신체 정보를 공개 레포에 노출하지 않는다")에 따라 **체중 등 민감 수치는
여기 두지 않는다** — 목표값은 "조깅 25분"처럼 루틴 파라미터 수준으로만 둔다.

**시트 스키마**: 체크인 행에 `person` 컬럼을 추가하고, 조회 시 `person`으로 필터한다.

**마이그레이션(필수)**: 기존 행에는 `person`이 없다. 마이그레이션 스크립트로 기존 전체 행에
`jammy`를 채운다. 이 마이그레이션 없이 필터를 켜면 배우자의 과거 이력이 통째로
사라져 보이고(완료율·연속일수·리포트 탭 전부 0이 된다) C-1이 깨진다.

**정적 데이터 경로**: `docs/data/<personId>/{current-week,exercise-stats,nutrition-stats}.json`
으로 사람별 분리. `history/`도 `history/<personId>/` 하위로 분리한다.

**라우팅**: 사람별 고유 URL(`?person=<personId>`). 프론트가 이 값으로 자기 사람의
`docs/data/<personId>/`를 읽고, 체크인 POST 시 `person`을 함께 보낸다.

**`person` 파라미터가 없을 때**: 어떤 사람의 데이터도 보여주지 않고 "링크를 확인해주세요"
안내만 표시한다. 특정 사람을 기본값으로 두지 않는 이유 — 루트 URL을 아는 누구에게나 그
사람의 루틴이 노출되고, 나중에 기본 사용자를 바꾸면 조용히 다른 사람 데이터가 뜬다.

**따라서 배우자의 기존 홈화면 아이콘은 루트 URL을 가리키므로 동작하지 않게 된다** — 오퍼레이터
(rainny)가 배포 후 배우자 아이폰에서 새 URL로 홈화면을 재추가해야 한다. 사용자가 URL 변경을
허용했고 오퍼레이터가 기기를 직접 만질 수 있는 관계이므로 수용 가능하다. 이 작업은
운영 런북(`specs/plans/operator-runbook.md`)의 배포 절차에 체크리스트 항목으로 추가한다.

### S-3. 테마 — 모티프 프리셋 방식

**중요 — 이건 색상 테마가 아니라 소재(모티프) 테마다.** 사용자가 제공한 자산 6종을 분석한
결과, 6개 테마가 **동일한 파스텔 수채화 팔레트를 공유**한다(크림색 배경, 민트/라벤더/코랄
얼룩까지 같음). 달라지는 것은 색이 아니라 **그림의 소재**다.

따라서 `tokens.css`의 색 변수는 **전 테마 공통으로 유지**하고, 테마 전환은 **이미지 자산
경로만 바꾸는 것**으로 구현한다. 애초 계획했던 "테마별 CSS 변수 세트"는 불필요하다 —
접근성 대비(WCAG AA) 검증도 팔레트가 하나뿐이므로 1회만 하면 된다.

**테마 목록** (사용자 제공 자산 기준, 6종):

| themeId | 히어로 소재 | 장식 스티커 |
|---|---|---|
| `wellness` | 요가매트·덤벨·샐러드·캔들·저널 | 요가매트, 물병, 덤벨, 샐러드볼, 캔들 |
| `travel` | 캐리어·카메라·지도·여권·모자 | 캐리어, 여권, 지도, 모자 |
| `space` | 망원경·우주헬멧·토성·로켓 | 망원경, 헬멧, 토성, 로켓, 위성 |
| `urban` | 자전거·노트북·운동화·도시풍경 | 자전거, 노트북, 운동화, 커피, 도시 |
| `cinema` | 클래퍼보드·필름릴·팝콘·프로젝터 | 클래퍼보드, 필름릴, 팝콘, 프로젝터, 티켓, 3D안경 |
| `study` | 책·노트·펜·램프·커피 | 책더미, 노트, 펜꽂이, 안경+문구, 램프 |

### S-3.1 스티커의 두 종류 — 아이템 스티커 vs 장식 스티커 (분리)

**이 둘은 성격이 완전히 달라 반드시 분리한다.**

| | 아이템 스티커 | 장식 스티커 |
|---|---|---|
| 역할 | 그 루틴이 **무엇인지** 식별 (조깅→운동화, 식단→샐러드볼) | 페이지에 **개성**을 부여 |
| 묶이는 축 | **카탈로그 아이템** | **테마** |
| 테마 영향 | **없음 — 전 테마 공용** | 테마별로 다름 |
| 위치 | `docs/assets/images/stickers/` (현행 유지) | `docs/assets/themes/<themeId>/stickers/` |

**분리하는 이유**: 아이템 스티커를 테마에 묶으면 `cinema` 테마 사용자가 스쿼트를 할 때
팝콘 스티커가 뜬다. 스쿼트는 어떤 테마에서든 스쿼트이므로, 기능적 식별자는 테마와 무관해야
한다.

제공된 6세트 중 **`wellness`만 우연히 아이템과 매핑된다**(요가매트·물병·덤벨·샐러드볼 =
운동·물·근력·식단). 이는 wellness가 이 앱의 원래 도메인이기 때문이며, 나머지 5개 테마의
스티커는 루틴 아이템에 대응되지 않는다. 따라서 **제공된 30여 장은 전부 장식 스티커로
분류**하고, 아이템 스티커는 기존 12종을 그대로 쓴다.

### S-3.2 장식 슬롯

장식 스티커를 배치할 UI 슬롯을 신설한다. 슬롯은 **기능적 의미가 없는 여백**에만 두어,
스티커가 없거나 개수가 부족해도 화면이 깨지지 않게 한다.

| 슬롯 | 위치 | 개수 |
|---|---|---|
| 히어로 하단 액센트 | `.hero-card` 아래쪽 모서리 | 1~2 |
| 주간 요약 헤더 | 리포트 탭 상단 | 1 |
| 빈 상태 | 이력 없음 / 기록 없음 화면 | 1 |

**규칙**:
- 장식 스티커는 **`alt=""`** (장식이므로 스크린리더가 읽지 않는다) — 아이템 스티커도 현재
  `alt=""`이지만 이쪽은 의도적 장식이라는 점이 다르다.
- 테마의 장식 스티커가 슬롯 수보다 적으면 **있는 만큼만 쓰고 나머지 슬롯은 비운다**(반복
  배치하지 않는다).
- `pastel`(jammy)은 **장식 슬롯을 비워둔다** — 슬롯이 추가되어도 jammy 화면에는 아무것도
  나타나지 않아야 C-1(시각적 무변화)이 지켜진다.
- 장식 슬롯은 레이아웃 높이에 영향을 주지 않도록 배치한다(절대 위치 또는 기존 여백 안).

**jammy(기존 사용자)는 현행 `pastel` 자산을 그대로 유지한다** — 위 6종 중 하나로 바꾸지
않는다. 화면이 시각적으로 변하면 C-1 위반이다. `pastel`은 7번째 themeId로 등록하고 jammy
전용으로 둔다.

**히어로 이미지 — 가로형을 그대로 사용한다.** 제공된 원본은 1448×1086 가로형이고 앱이 현재
쓰는 모바일 세로형은 800×1000이지만, **세로 크롭을 하지 않는다.** 근거: `style.css`의
`.hero-card img`가 `width: 100%`만 지정하고 **높이 고정값이 없어** 어떤 비율이든 레이아웃이
깨지지 않는다. 또한 앱은 이미 640px 초과 화면에서 가로형(`dashboard-hero-768.webp`)을 쓰고
있어 가로 히어로는 검증된 경로다. 세로 크롭은 "왼쪽 여백 + 오른쪽 오브젝트" 구도상 오브젝트가
잘릴 위험만 있고 얻는 것이 없다. 각 테마당 히어로는 **가로 1종을 리사이즈해 사용**한다.

**장식 스티커는 시트에서 개별 분리한다.** 제공된 스티커 시트 3장(1536×1024 RGBA)에 6개
테마의 장식 스티커가 나뉘어 담겨 있다. 투명 배경 기반 연결요소 검출로 자동 분리가 가능함을
확인했다(시트당 10~11개 검출). 다만 한 스티커가 두 덩어리로 잡히는 경우가 있어 **분리 결과는
육안 확인이 필요**하다. 이 작업은 구현 5단계(장식 슬롯)에 속하며, 아이템 스티커와는 무관하다
(S-3.1).

**PWA 아이콘·favicon·로고는 전 테마 공용으로 유지한다** — 테마별로 만들지 않는다. 홈화면
아이콘은 앱 진입 전에만 보이고, 사람별로 달라야 할 기능적 이유가 없다. 여러 명이 각자
홈화면에 추가하면 아이콘이 모두 같아 구분이 안 되는 불편은 있으나, 테마별 아이콘 3종씩을
만들고 유지하는 비용보다 작다고 판단했다.

**테마 자산 경로**: `docs/assets/themes/<themeId>/hero.webp` + `.../stickers/*.webp`(장식).
**아이템 스티커(`docs/assets/images/stickers/`)와 공용 자산(PWA 아이콘·favicon·로고·내비
아이콘)은 현재 위치를 유지한다** — 테마 폴더로 옮기지 않는다(S-3.1).

**내비게이션·카테고리 SVG 아이콘 12종은 테마 작업 대상이 아니다** — `currentColor`를 쓰고
있어 CSS 색 변수를 따라가며, 팔레트가 공통이므로 애초에 바뀌지 않는다.

### S-4. 주간 크론 루프화

`weekly_refresh.main()`이 `people/` 전체를 순회하며 사람별로 기존 `run()`을 호출한다.

- **사람 단위 예외 격리**: 한 사람의 실패(시트 응답 없음 등)가 다른 사람의 처리를 막지 않는다.
- **커밋/푸시는 전체 루프 종료 후 1회** — 사람마다 커밋/푸시하면 GitHub Pages 재배포가 사람
  수만큼 발생한다. 현재의 `commit_and_push()` 브랜치 안전장치(main이 아니면 거부)는 유지한다.
- **텔레그램 알림은 rainny에게 1건으로 묶어 발송** — 사람별 요약을 한 메시지에 담는다.
  실패한 사람이 있으면 그 사람과 실패 사유를 함께 표시한다.
- `active: false`인 사람은 건너뛴다.

### S-5. 마이그레이션 검증 게이트

배포 전 필수 단계. 마이그레이션 **전** 배우자 페이지의 완료율·운동 연속일수·리포트 탭 내용·
주간 이력을 스냅샷으로 기록하고, 마이그레이션 **후** 동일 값이 나오는지 대조한다. 불일치가
있으면 배포를 중단한다. reviewer PASS와는 별개의 게이트다(reviewer는 코드 품질, 이건 기존
사용자 영향 확인).

## 구현 순서 권고

이 설계는 여러 작업 흐름을 담고 있어 한 번에 구현하면 마이그레이션 리스크가 커진다. 아래 7단계를
권고한다 — 각 단계는 앞 단계에 의존하고, S-5 검증은 마지막이 아니라 마이그레이션 직후에 온다.

1. **아이템 카탈로그 + 규칙 템플릿**(S-1) — 순수 Python, 외부 의존 없음. 배우자 아이템을
   카탈로그로 등록하고 **기존 완료율/제안 출력이 바이트 단위로 동일한지** 단위 테스트로 고정.
2. **사람 설정 파일 + 경로 분리**(S-2 전반) — `people/`, `docs/data/<personId>/`,
   `history/<personId>/`. 이 시점까지는 배우자 1명만 존재하며 동작이 같아야 한다.
3. **시트 스키마 + 마이그레이션**(S-2 후반) — `person` 컬럼 추가, 기존 행 백필,
   Apps Script 조회 필터. **여기서 S-5 검증 게이트를 통과해야 다음으로 간다.**
4. **프론트 라우팅 + 히어로 테마**(S-2 라우팅, S-3) — URL person 파싱, 히어로만 테마별 전환.
   원본 킷은 `assets-source/theme-kit-2026-07-31/`에 보관되어 있다(히어로 6 + 스티커 시트 3).
   1회용 처리 스크립트로 히어로 리사이즈 → `docs/assets/themes/<themeId>/hero.webp`.
   **아이템 스티커는 건드리지 않는다**(S-3.1). jammy는 기존 `pastel` 자산 그대로.
5. **장식 슬롯 + 장식 스티커**(S-3.2) — 4단계와 분리한다. 슬롯 신설은 UI 변경이라
   리스크가 다르고, 4단계까지만으로도 다중 사용자 앱은 완성되기 때문이다. 스티커 시트를
   분리해 `docs/assets/themes/<themeId>/stickers/`에 넣고 슬롯에 배치.
   **분리 결과는 육안 확인 필수**(한 스티커가 두 덩어리로 잡히는 경우가 있음).
   **jammy의 장식 슬롯이 비어 있는지 확인**해야 C-1이 지켜진다.
6. **크론 루프화**(S-4) — people 순회, 예외 격리, 커밋/알림 1회.
7. **신규 사용자 1명 온보딩** — 2번째 사람을 실제로 추가해 다중 사용자 동작을 검증.
