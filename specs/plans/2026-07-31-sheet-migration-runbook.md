# 시트 마이그레이션 실행 안내 (Task 11 — 수동)

이 문서는 rainny가 직접 수행하는 절차다. 구글시트·Apps Script 편집기 조작이라 자동화할 수 없다.

**소요 시간**: 15~20분. **중간에 멈추면 안 되는 구간이 있다**(3~5단계) — 시간을 확보하고 시작할 것.

---

## 왜 필요한가

Task 9에서 Apps Script가 `person` 컬럼을 A열로 쓰도록 바뀌었다. 하지만 **라이브 스프레드시트의
기존 행에는 person 값이 없다.** 이 상태로 새 코드를 배포하면 `doGet`이 `person === 'jammy'`로
필터하는데 기존 행은 빈 값이라 **배우자님 과거 이력이 화면에서 통째로 사라진다.**

그래서 기존 행에 `jammy`를 채우는 마이그레이션이 필요하다.

## ⚠️ 시작 전 필수 확인

- [ ] **배우자님이 지금 체크인 중이 아닌지 확인.** 3~5단계 사이에 체크인이 들어오면 행이
      어긋난다(아래 "위험 구간" 참고).
- [ ] 일요일 18:00 크론까지 시간이 남아 있는지 확인. 마이그레이션 도중 크론이 돌면 안 된다.
- [ ] `.env`의 `ROUTINE_APPS_SCRIPT_URL`을 손댈 일이 없는지 확인 — **배포 URL이 바뀌면 안 된다**
      (5단계에서 "새 배포"가 아니라 "기존 배포 수정"을 해야 하는 이유).

## 위험 구간 (3~5단계)

시트 스키마를 바꾼 시점부터 새 코드를 배포 완료할 때까지, **실행 중인 코드와 시트 구조가
어긋나 있다.** 이 구간에 체크인이 들어오면 컬럼이 밀린 행이 기록된다.

→ **3단계 시작 후 5단계 완료까지 쉬지 말고 이어서 할 것.** 5~10분이면 끝난다.

---

## 1단계 — 마이그레이션 전 스냅샷 기록 (검증 기준선)

배포된 앱을 열어 아래 값을 **적어둔다.** 마이그레이션 후 이 값들과 대조하는 것이 성공 판정
기준이다. 눈으로만 보고 넘어가면 나중에 비교할 수 없다.

```
weekId:                    ____________________
카테고리별 완료율 (7개):
  슬로우 조깅  ____%    스쿼트  ____%    데드리프트  ____%
  런지  ____%          플랭크  ____%    간식섭취  ____%
  바이올린  ____%
운동한 날:  ____ / 7일        연속:  ____ 일째
리포트 탭 - 이번 주 식사 기록 행 수:  ____
리포트 탭 - 주간 평균:  ____ kcal / 탄 ____g / 지 ____g / 단 ____g
```

> 리포트 탭에 통계가 아직 안 보이면 그것도 그대로 적어둔다("없음"). 주간 리프레시가 아직 한 번도
> 완주하지 않아 `exercise-stats.json`·`nutrition-stats.json`이 없는 상태가 정상이다.

## 2단계 — 스프레드시트 백업

구글시트에서 **파일 > 사본 만들기**. 이름에 날짜를 넣는다:
`routine-jammy responses 백업 2026-07-31`

- [ ] 사본이 만들어졌고 원본과 행 수가 같은지 확인

**이 백업이 유일한 되돌리기 수단이다.** 건너뛰지 말 것.

---

## 여기서부터 위험 구간 — 멈추지 말고 5단계까지

## 3단계 — 마이그레이션 함수 추가

Apps Script 편집기(script.google.com)에서 이 프로젝트를 열고, 파일을 하나 추가해
`apps-script/migrate-person-column.gs`의 내용을 붙여넣는다.

## 4단계 — 마이그레이션 실행

편집기에서 `migratePersonColumn` 함수를 선택해 **실행**한다.

기대 로그:
```
responses: N행에 person=jammy 채움
reflections: M행에 person=jammy 채움
```

- [ ] N이 0이 아닌지 확인. 앱이 2026-07-26 배포됐고 현재 2026-W31이므로 **N은 대략 60~130** 범위다.
      0이 나오면 시트 이름이 다른 것이니 중단하고 확인한다.
- [ ] 두 번 실행해도 안전하다(이미 마이그레이션된 시트는 건너뛴다). 실패해서 재실행해도 된다.

**시트를 열어 눈으로 확인:**
- [ ] A열 헤더가 `person`이고 모든 데이터 행에 `jammy`가 들어있다
- [ ] B열이 `weekId`, C열이 `day`, D열이 `item`으로 한 칸씩 밀렸다
- [ ] 빈 person 셀이 없다

## 5단계 — 갱신된 Code.gs 배포

편집기에서 `apps-script/Code.gs`의 현재 내용을 붙여넣고, **배포 > 배포 관리 > (기존 배포) 편집
> 새 버전**으로 배포한다.

- [ ] **"새 배포"를 만들면 URL이 바뀐다 — 반드시 기존 배포를 수정할 것.**
- [ ] 배포 후 URL이 `.env`의 `ROUTINE_APPS_SCRIPT_URL`과 같은지 확인

**여기까지 오면 위험 구간 종료.**

## 6단계 — 검증 게이트 ①: 데이터가 돌아오는가

```bash
cd ~/dev-out/routine-jammy
set -a && source .env && set +a
python3 -c "
import sys; sys.path.insert(0, 'src/routine-jammy')
from sheet_client import fetch_week
data = fetch_week('2026-W31', person='jammy')
print('응답 행 수:', len(data['responses']))
print('회고:', data.get('reflection'))
"
```

- [ ] 응답 행 수가 **0이 아니고** 마이그레이션 전과 같다

> **0이 나오면 즉시 중단.** person 필터나 컬럼 인덱스가 잘못된 것이다. 5단계에서 붙여넣은
> `Code.gs`의 `doGet`이 최신인지 다시 확인한다.

## 7단계 — 검증 게이트 ②: 화면 값이 같은가

```bash
cd ~/dev-out/routine-jammy/docs && python3 -m http.server 8899
```

브라우저에서 `http://localhost:8899/?person=jammy` 를 열고 **1단계에 적어둔 값과 전부 대조**한다.
확인 후 `Ctrl+C`.

- [ ] 완료율 7개가 1단계와 동일
- [ ] 운동한 날 / 연속일수가 1단계와 동일
- [ ] 리포트 탭 내용이 1단계와 동일

> **하나라도 다르면 배포하지 말고 원인을 찾는다.** 이것이 C-1(기존 사용자 무영향) 검증이다.

## 8단계 — 검증 게이트 ③: 체크인 왕복

로컬 서버(또는 배포된 앱)에서 오늘 항목 **하나를 체크했다가 다시 해제**한다.

- [ ] 스프레드시트에서 해당 행의 `person`이 `jammy`로 채워진다
- [ ] **새 행이 추가되지 않고 기존 행이 갱신된다** (중복 판정 키에 person이 들어갔는지 확인하는 것)

## 9단계 — 크론 실경로 확인

일요일 크론이 실제로 도는 경로가 살아있는지 확인한다(네트워크 호출 없이 시그니처만 검사):

```bash
cd ~/dev-out/routine-jammy
python3 -c "
import sys, inspect; sys.path.insert(0, 'src/routine-jammy')
import weekly_refresh, sheet_client
d = inspect.signature(weekly_refresh.run).parameters['fetch_week_fn'].default
print('기본 fetch가 sheet_client.fetch_week인가:', d is sheet_client.fetch_week)
print('person 수용:', 'person' in inspect.signature(d).parameters)
"
```

- [ ] 둘 다 `True`

## 10단계 — 브랜치 병합

여기까지 전부 통과했으면 `feature/multi-person-backend`를 `main`에 병합한다.

**병합 전 확인:**
- [ ] `main`에서 크론이 도는 구조이므로, 병합 전까지는 크론이 **feature 브랜치 체크아웃**을
      실행한다는 점을 인지할 것. `commit_and_push()`에 브랜치 안전장치가 있어 main이 아니면
      push를 거부하므로 데이터가 망가지진 않지만, 주간 리프레시가 실패로 끝난다.
- [ ] 일요일 18:00 이전에 병합을 마치는 것이 안전하다.

## 문제가 생기면

| 증상 | 원인 | 대응 |
|---|---|---|
| 6단계에서 행 수 0 | `doGet`의 person 필터/컬럼 인덱스 오류 | `Code.gs` 재배포. 그래도 안 되면 백업 시트로 복구 |
| 7단계 값 불일치 | 컬럼 인덱스가 밀림 | 백업 시트로 복구 후 3단계부터 다시 |
| 8단계에서 행이 중복 생성 | 중복 판정 키에 person 누락 | `doPost` 재확인 후 재배포. 중복 행은 수동 삭제 |
| 4단계 로그가 "이미 마이그레이션됨" | 이미 실행했음 | 정상. 다음 단계로 |

**복구 방법**: 2단계 백업 사본의 내용을 원본에 덮어쓰고, Apps Script를 마이그레이션 전
버전(`git show 8bb892f~1:apps-script/Code.gs`)으로 되돌린다.
